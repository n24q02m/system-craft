# P15-03-L09 — Lab cụm P9: kind — Deploy, Scale, và Tự chữa Pod

> **Tầng:** Học · **Văn kiện học cụm P9** · **Làm khi:** sau quiz Q09 · **Thời lượng:** 60–90 phút
> **Bản:** SA-2028.1 · **Cần:** Linux/macOS có **Docker** + kubectl + kind — sandbox/container không chạy được (cần Docker daemon thật)

---

## 1. Mục tiêu

Biến các khái niệm nằm trong 9.1 (Deployment/Pod/kubelet/probe) thành hành động tay: deploy một dịch vụ, scale nó, **giết pod** và thấy control plane tự chữa, rồi **làm hỏng ứng dụng** và thấy trạng thái `CrashLoopBackOff` — kèm readiness probe chặn lưu lượng vào pod chưa khoẻ.

## 2. Môi trường tối thiểu

Docker chạy được + `kind` (Kind = Kubernetes in Docker — cụm K8s thật chạy trong container) + `kubectl`. RAM tối thiểu ~4 GB trống.

## 3. Bước

1. `kind create cluster --name lab` (khoảng 1 phút) → `kubectl get nodes` — một node `control-plane` `Ready`.
2. Triển khai:

```yaml
# deploy.yaml
apiVersion: apps/v1
kind: Deployment
metadata: {name: web}
spec:
  replicas: 2
  selector: {matchLabels: {app: web}}
  template:
    metadata: {labels: {app: web}}
    spec:
      containers:
      - name: web
        image: nginx:1.27
        readinessProbe: {httpGet: {path: /, port: 80}, initialDelaySeconds: 2}
```

`kubectl apply -f deploy.yaml && kubectl get pods -w` — chờ 2 pod `Running` + `READY 1/1`.
3. **Scale:** `kubectl scale deploy/web --replicas=5` → `get pods -w` thấy 3 pod mới; scale về 2.
4. **Giết pod:** `kubectl delete pod -l app=web --wait=false` một pod → `get pods -w`: pod chết, Deployment tạo pod mới trong vài giây ( ReplicaSet giữ đúng số bản sao).
5. **Làm hỏng:** `kubectl set image deploy/web nginx=nginx:1.27-nonexist` → `get pods -w` thấy `ErrImagePull` → `ImagePullBackOff`; `kubectl rollout undo deploy/web` phục hồi.
6. **CrashLoop:** `kubectl set image deploy/web nginx=busybox` + `kubectl patch deploy/web -p '{"spec":{"template":{"spec":{"containers":[{"name":"web","command":["sleep","1"]}]}}}}'` → container thoát ngay lập tức → `CrashLoopBackOff` với backoff tăng dần (10s, 20s, 40s…). `rollout undo` để dọn.

## 4. Kết quả mong đợi

`kubectl get pods` cho bảng `NAME READY STATUS RESTARTS AGE`: bước 2 → `Running 1/1` (readiness probe mới cho `READY` lên 1 — pod chưa probe xong thì `READY 0/1` dù `Running`); bước 4 → pod mới thay thế trong ~vài giây, `AGE` của nó bằng 0; bước 5–6 → `ImagePullBackOff`/`CrashLoopBackOff` và **cột `RESTARTS` tăng dần theo nhịp backoff** — kubelet giật container lại theo lùi dần (9.1 §5). Điều lab muốn bạn "aha": **Kubernetes không sửa gì cho bạn** — nó chỉ lặp lại khai báo mong muốn (deploy 2 bản web) đối lại hiện thực, còn app hỏng thì vẫn hỏng vĩnh viễn ở `CrashLoopBackOff` — phân biệt control plane khoẻ và ứng dụng khoẻ.

## 5. Tự chấm

- Giải thích được khác nhau `Running` và `READY 1/1` (process sống ≠ sẵn sàng nhận lưu lượng — readiness probe);
- Nêu điều gì xảy ra nếu vừa scale vừa giết node worker (hai cơ chế khác nhau cùng can thiệp — 9.1, 9.2);
- Đối chiếu bài toán thực chiến: service của bạn 3 pod, 1 pod `CrashLoopBackOff` — người dùng có thấy lỗi không, và metric nào báo cho bạn (p99 vẫn ổn vì 2 pod còn sống — 11.2, cân nhắc PodDisruptionBudget — 9.1).
