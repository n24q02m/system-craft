# P15-03-L05 — Lab cụm P5: Query Plan trước/sau khi thêm Index

> **Tầng:** Học · **Văn kiện học cụm P5** · **Làm khi:** sau quiz Q05 · **Thời lượng:** 30–45 phút
> **Bản:** SA-2028.1 · **Cần:** Python 3 (sqlite3 sẵn trong stdlib) — không cần server DB

---

## 1. Mục tiêu

Đo bằng tay câu chuyện kinh điển của 5.1–5.2: cùng một truy vấn, `SCAN` toàn bảng so với `SEARCH` bằng index chênh nhau **hàng trăm lần** — và hiểu *vì sao* kế hoạch đổi: `EXPLAIN QUERY PLAN` nói ra bằng lời trước khi thời gian nói ra bằng số.

## 2. Môi trường tối thiểu

Python 3. Tải: 2 triệu dòng sự kiện, trong đó user 777 có 5.000 sự kiện `buy` dồn trong một cửa sổ thời gian.

## 3. Bước

1. Lưu `l05.py` và chạy `python3 l05.py`:

```python
import sqlite3, time, random, os
f = 'l05.db'
db = sqlite3.connect(f)
db.execute('PRAGMA journal_mode=WAL')
db.execute('CREATE TABLE events (id INTEGER PRIMARY KEY, user_id INTEGER,'
           ' kind TEXT, ts INTEGER, payload TEXT)')
random.seed(42)
def rows():
    for i in range(5000):                      # user 777: 5.000 'buy' trong cửa sổ hẹp
        yield (777, 'buy', 1_750_000_000 + i, 'x' * 40)
    for i in range(2_000_000):                 # nền: 2 triệu dòng ngẫu nhiên
        yield (random.randint(1, 200000), random.choice(
            ['login','view','click','buy','error']), 1_700_000_000 + i, 'x' * 40)
db.executemany('INSERT INTO events (user_id, kind, ts, payload) VALUES (?,?,?,?)', rows())
db.commit()

SQL = ('SELECT COUNT(*) FROM events WHERE user_id = 777 AND kind = "buy" '
       'AND ts BETWEEN 1_750_000_000 AND 1_750_050_000')

def run(label):
    for p in db.execute('EXPLAIN QUERY PLAN ' + SQL):
        print('   %s plan: %s' % (label, p[-1]))
    best = 9e9
    for _ in range(5):
        t = time.time(); n = db.execute(SQL).fetchone()[0]; best = min(best, time.time() - t)
    print('   %s: %.2f ms · đếm được %d dòng' % (label, best * 1000, n))
    return best

t0 = run('TRƯỚC index')
db.execute('CREATE INDEX idx ON events (user_id, kind, ts)')
t1 = run('SAU index  ')
print('tăng tốc: ~%.0f lần' % (t0 / t1))
for x in (f, f + '-wal', f + '-shm'):
    if os.path.exists(x): os.remove(x)
```

2. Chạy lại với thứ tự cột index đảo: `CREATE INDEX idx2 ON events (ts, kind, user_id)` — xem plan và thời gian thay đổi thế nào.

## 4. Kết quả mong đợi

Đo thật (SQLite 3.46, Linux, 04/11/2026): `TRƯỚC index` → plan `SCAN events`, **85,19 ms**; `SAU index` → plan `SEARCH events USING COVERING INDEX idx (user_id=? AND kind=? AND ts>? AND ts<?)`, **0,20 ms** — nhanh hơn **~436 lần**. Hai chi tiết đáng chú ý hơn con số: (1) `COVERING INDEX` nghĩa là SQLite không phải đụng vào bảng gốc nữa — index đã chứa mọi cột truy vấn cần (5.1 §2: B-tree giữ `(user_id, kind, ts)` và `id`); (2) index đảo thứ tự (`ts, kind, user_id`) cho plan tệ hơn hoặc vẫn SCAN — cột bằng nhau (`user_id=`, `kind=`) phải đứng trước cột dải (`ts BETWEEN`) đúng thứ tự chọn lọc. Máy bạn khác con số tuyệt đối, nhưng tỷ lệ SCAN/SEARCH giữ nguyên bậc.

## 5. Tự chấm

- Giải thích được `COVERING` nghĩa là gì và vì sao query này "may mắn" (mọi cột nằm trong index — `COUNT(*)` không cần cột khác);
- Nêu được quy tắc thứ tự cột index cho 1 query thật của bạn (bằng-phía-trước, dải-phía-sau) và cái giá phải trả khi ghi (mỗi INSERT giờ phải cập nhật thêm B-tree — 5.2);
- Trả lời: index có phải luôn tốt không — khi nào nhiều index làm hệ **chậm** (ghi nhiều, đọc ít, RAM không đủ giữ trang nóng — 5.16).
